# Written answers

## 1. How would you add login with AWS Cognito + Amplify to this app?

I haven't used Cognito in production yet, but I looked into it: read the docs and talked it through with AI. Here's the plan. Right now the user is identified in one place, a guard on the API that reads the `x-user-id` header, and I built it that way on purpose so the switch stays simple. I'd create a User Pool, add Amplify on the frontend for sign-in, and Apollo would send the access token in the `Authorization` header instead of `x-user-id`. On the API only the guard changes: it verifies the Cognito token (signature, expiry, which app client it was issued for) and finds the user by their Cognito id, while resolvers, services and ownership checks stay the same.

## 2. How would you add image upload to S3 for bottle photos?

I've used S3 before, and in my own project CodeVault files are stored in Cloudflare R2, an S3-compatible storage, through the same AWS S3 SDK. Here's the plan. The file shouldn't go through our API: the browser uploads it straight to S3 with a temporary link (a presigned URL) that the API issues. When it issues the link, the API limits the file type, the size and the path in the bucket, for example a folder per user. After the upload the bottle stores the S3 key instead of an external URL like now, and the API checks that the file is in the current user's folder. The bucket itself stays private, and photos are served through CloudFront.

## 3. How would you add chat between users with Stream (GetStream)?

In one of the commercial apps I worked on the chat, which was built on TalkJS, a service of the same kind as Stream, so the approach is familiar to me. I could build a custom chat on WebSockets too, but a ready-made service gives message history, online status, unread counts and moderation out of the box, so for a platform it's a sensible choice. The Stream secret key lives only on our API: after our usual authentication, the API creates the user in Stream with the same id and name as in our database and issues a token, which the frontend refreshes automatically when it expires. Channels between two users are also created by the server, so the rules for who can message whom stay with us and not with the client, and Stream itself makes sure only channel members can read it. On the frontend we use Stream's ready-made React components for the chat list and the conversation, and Stream notifies our API about new messages through webhooks, for example to send an email when the user is offline.

## 4. How do you make a database change safely on a live platform with real users?

The main thing I keep in mind is that during a deploy the old and the new version of the app run at the same time for a while. So a migration must not break either of them, and I split risky changes into several steps. For example, to rename a column I first add the new one, copy the data into it and switch the code, and drop the old column only in the next release. Migrations run as a separate deploy step, not on app start. In my own NestJS project on AWS I did exactly that, migrations run there as a separate task in ECS. Before a migration you need a backup and a check on staging, and every migration should have a rollback.

## 5. How do you review code written by an AI tool before merging it?

I work spec-driven, on my own Claude Code harness that I carry from project to project, and a lot is built into it structurally: coding standards, working rules for the AI and guardrails, for example the AI never commits or pushes without my approval. First a project overview, then it is split into small specs with acceptance criteria, and I review both before any code is written and edit them: I cut the scope when a spec grows too big, move nice-to-haves into an optional section, pick the implementation option I prefer, or add what the AI missed. Every spec goes through the same cycle of skills (load, start, test, review, complete), so the AI never writes everything at once, and I read every diff myself. My own part is writing the rules the AI works by (coding standards, the git process), making the call at every point where the AI offers options, and before each merge walking through the testing steps by hand in the browser and with requests to the API, including checking the UI on mobile and desktop. For critical parts like authorization, I use /feature explain to walk through the code file by file, so I understand and can defend everything I merge. Strict TypeScript, the linter and tests catch the basics, before every merge my custom code-scanner agent reviews the diff for security and performance issues, and I check APIs against the docs of the installed library versions through Context7, so the AI doesn't use things that don't exist. For important tests I break the code on purpose to make sure the test actually fails, and before the PR I go through the whole diff looking for generation leftovers, like debug logs, commented-out code and comments that just restate the code. For important parts I sometimes give the code to another model for a separate review, Claude in a fresh session or Codex, because an independent reviewer doesn't grade its own work and catches what the first one missed. This repo was built exactly this way, the specs are in `context/features/`, and the decisions, including the ones where I disagreed with the AI's first choice, are in `docs/decisions.md`.
